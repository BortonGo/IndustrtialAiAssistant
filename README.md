# Local Assistant

Local Assistant — настольное приложение на C++ и Qt для работы с документами и мониторинга состояния компьютера. Приложение использует локальные языковые модели для формирования ответов, RAG для поиска информации в документах и MCP для получения системных показателей.

Цель проекта — предоставить единый интерфейс для запросов к документам и данным компьютера с отображением источников ответа. Проект находится в активной разработке.

## Что уже работает

- Интерфейс чата с несколькими диалогами и переключением между ними.
- Загрузка TXT, PDF с текстовым слоем и DOCX, проверка дубликатов и отображение состояния индексации.
- Асинхронное извлечение текста из PDF через Poppler (`pdftotext`) и из DOCX через Python (`python-docx`), с обработкой ошибок и таймаутом.
- Разбиение текста на чанки, пакетное получение embeddings и поиск подходящих фрагментов для ответа.
- Генерация ответов через локальный сервер LM Studio.
- Получение загрузки CPU и RAM через собственный MCP-сервер на Python.
- Отображение источников ответа и тёмная тема интерфейса.
- Отображение Markdown в ответах ассистента через преобразование в HTML библиотекой MD4C. Сообщения пользователя отображаются обычным текстом.

Пока чаты и индекс хранятся в памяти и не сохраняются между запусками. TXT читаются в UTF-8; текст из PDF и DOCX также извлекается в UTF-8. DOCX поддерживает чтение абзацев и строк обычных таблиц в порядке документа. Формат DOC, OCR, извлечение и понимание изображений пока не реализованы: сканы PDF без текстового слоя не поддерживаются.

Размер исходного файла ограничен 1 МиБ для всех трёх форматов. На извлечение текста из PDF или DOCX отводится 30 секунд. Каждый из этих обработчиков читает один файл за раз; повторный запрос к занятому обработчику отклоняется. Ограничение относится к размеру файла на диске: небольшой DOCX может содержать много текста, поскольку его содержимое сжато.

После чтения все документы проходят общую очередь индексации. Чанки имеют размер до 500 символов QString (единиц UTF-16) с перекрытием 100. Embeddings запрашиваются пакетами до 16 текстов: одновременно отправлен один пакет, следующий начинается после сохранения результатов предыдущего. Последний пакет может быть меньше. Ответы сопоставляются с текстами по полю `index`; проверяются количество результатов, индексы, размерность и числовые значения векторов. При ошибке индексации векторы этого документа удаляются, документ получает статус ошибки.

Вопрос пользователя получает отдельный embedding; поиск возвращает до трёх наиболее близких чанков. История сообщений хранится в памяти для отображения, но пока не передаётся модели как история диалога.

## Стек

C++17, Qt 5 Widgets и Network, CMake. Текущая сборка проверена с Qt 5.7 и MinGW 5.3 (32 бита). Для чтения PDF — утилита Poppler `pdftotext`, запускаемая через `QProcess`. Для DOCX — отдельный процесс Python с `python-docx==1.2.0`; для MCP-сервера — Python, MCP SDK и psutil. Окружения Python проверены с Python 3.13. MD4C 0.5.2 собирается из исходников на C и статически связывается с приложением. Сейчас использую EmbeddingGemma для поиска по документам и Qwen3-14B для генерации ответов через LM Studio.

## Структура исходников

- `include/` — заголовки `.h` и `.hpp`.
- `src/` — реализации `.cpp` и точка входа `main.cpp`; форма окна остаётся в `src/ui/`.
- В обеих папках сохраняется разделение на `application`, `chat`, `documents`, `io`, `llm`, `mcp`, `rag` и `ui`.
- Например, объявление загрузчика находится в `include/io/document_loader.hpp`, реализация — в `src/io/document_loader.cpp`.
- `document_tools/` — скрипт чтения DOCX и список его зависимостей.
- `mcp_server/` — MCP-сервер для получения CPU/RAM.
- `third_party/md4c/` — исходники библиотеки преобразования Markdown в HTML, необходимые для сборки.
- `architecture/` — диаграммы целевой архитектуры и проект будущей БД.

Новые заголовки и реализации нужно добавлять в `CMakeLists.txt`. Актуальный способ сборки — CMake. `IndustrialAiAssistant.pro` сохранён как прежний проект qmake, но пока не обновлён под все новые обработчики документов и MD4C.

Чтение документов разделено на обработчики с общим интерфейсом `IDocumentReader`. `DocumentLoader` выбирает `TxtDocumentReader`, `PdfDocumentReader` или `DocxDocumentReader` по расширению файла и передаёт результат сигналом `documentReady`. `PdfTextExtractor` и `DocxTextExtractor` управляют внешними процессами, буферами и таймерами. `DocumentManager` добавляет готовый документ в библиотеку, а `AssistantService` запускает индексацию через `EmbeddingClient`.

Markdown преобразуется только при отображении ответа: `MessageWidget` вызывает `markdownToHtml()` из `src/ui/markdown_render.cpp` и показывает HTML через `QLabel`. В `ChatMessage` сохраняется исходный текст ответа. Внешний вид ограничен возможностями HTML, поддерживаемого Qt; это не браузерный движок.

## Запуск

1. Открыть `CMakeLists.txt` в Qt Creator и выбрать комплект Qt 5 с компиляторами C и C++, поддерживающим C++17 для кода приложения. Исходники MD4C должны находиться в `third_party/md4c/`.
2. В LM Studio подготовить модели `text-embedding-embeddinggemma-300m-qat` и `qwen/qwen3-14b`, запустить локальный API на `http://127.0.0.1:1234`. Имена моделей в запросах должны совпадать с идентификаторами, доступными серверу. Обработчик `/v1/embeddings` должен принимать массив текстов.
3. Из корня проекта создать отдельные окружения Python и установить зависимости:

   ```powershell
   python -m venv mcp_server/.venv
   ./mcp_server/.venv/Scripts/python.exe -m pip install -r mcp_server/requirements.txt psutil

   python -m venv document_tools/.venv
   ./document_tools/.venv/Scripts/python.exe -m pip install -r document_tools/requirements.txt
   ```

4. Проверить пути к Python и `server.py` в `src/mcp/mcp_client.cpp`: сейчас они заданы под папку `C:/Qt/IndustrialAiAssistant`. В `src/application/assistant_service.cpp` проверить `docxPythonPath` и `docxScriptPath`: сейчас они указывают на `document_tools/.venv/Scripts/python.exe` и `document_tools/read_docx.py` внутри этой же папки проекта.
5. Для PDF распаковать комплект Poppler для Windows вместе с DLL и остальными файлами, сохранив структуру каталогов. Проверить `pdfExtractorPath` в `src/application/assistant_service.cpp`: сейчас это `C:/Qt/IndustrialAiAssistant/tools/poppler-26.09.0/Library/bin/pdftotext.exe`. Если комплект находится в другом месте, изменить этот путь. Добавлять Poppler или Python в глобальный PATH не требуется: приложение запускает их по указанным путям.
6. Собрать и запустить приложение. MCP-сервер запускается из приложения автоматически; `pdftotext` и Python-скрипт DOCX запускаются при загрузке соответствующего документа. Сервер моделей LM Studio пока нужно запускать отдельно.

На другом компьютере окружения Python нужно создать заново, установить зависимости и подготовить Poppler, модели и сервер LM Studio. Пути к внешним процессам, адрес API и идентификаторы моделей пока заданы в коде; переносимые настройки и автоматический запуск сервера моделей ещё не реализованы. Для запуска готового `.exe` также понадобятся библиотеки и плагины Qt соответствующего комплекта.

## Проверка документов и интерфейса

Для локальных проверок подготовлены `test-document.pdf` и `test-document.docx` — небольшие документы с русским текстом и вымышленными данными. Тестовые PDF, корневой тестовый DOCX и папка `test-documents/` исключены через `.gitignore` и не появятся автоматически после клонирования репозитория. При их отсутствии можно использовать собственный небольшой документ с заранее известными фактами.

- PDF: загрузить `test-document.pdf`, дождаться статуса «Готов» и спросить: «Сколько датчиков установлено в проекте “Северный маяк”?». Ожидаемый ответ — 12; в источниках должны отображаться фрагменты этого PDF.
- DOCX: загрузить `test-document.docx`, проверить чтение абзацев до и после таблицы и спросить количество датчиков температуры. Ожидаемый ответ — 12; в источниках должен быть этот DOCX.
- Большие DOCX: локальные файлы `test-documents/load-test-100-pages.docx` и `test-documents/load-test-500-pages.docx` содержат разделы с явными разрывами страниц. Проверить поиск фактов из начала, середины и конца документа. Итоговая пагинация зависит от приложения, в котором открыт DOCX.
- Markdown: попросить ответ с заголовком, жирным текстом, списком и блоком кода. Проверить форматирование, переносы и выделение текста мышью.

Дополнительно проверить повторную загрузку того же документа, PDF без извлекаемого текста, пустой или повреждённый DOCX и загрузку обычного TXT. Ошибка чтения не должна мешать следующей попытке. Позиции источников обозначают смещения в извлечённом тексте, а не номера страниц PDF или DOCX.

В локальном замере обработки тестового DOCX на 500 страниц время снизилось с 35,29 до примерно 27 секунд после перехода на пакеты по 16 чанков. Это результат на текущем компьютере и модели, а не гарантированная скорость на другом оборудовании. Для сравнения использовать тот же документ и одинаковые границы замера, с уже загруженной моделью. Между повторными загрузками одного файла перезапускать приложение из-за проверки дубликатов.

## Дальше

Следующий обсуждаемый этап — переход с LM Studio на локальный `llama-server` из llama.cpp. Планируется отдельно проверить генерацию ответов и пакетные embeddings, вынести адреса API и параметры моделей в настройки, затем добавить запуск и остановку процессов через `QProcess`. Сейчас этот сервер и управление им ещё не реализованы.

После этого планируется сохранение чатов, документов и embeddings в SQLite. Также в планах: поддержка DOC, загрузка директорий, OCR и обработка изображений в документах. Для понимания изображений потребуется отдельный этап с подходящей мультимодальной моделью и передачей визуальных данных.

В папке `architecture` лежат диаграммы PlantUML с целевой архитектурой и проектом БД. Они описывают в том числе будущие возможности, которых в коде пока нет. Пометки о текущем состоянии в диаграммах могут отставать от реализации: поддержка PDF, DOCX и пакетных embeddings уже добавлена. Текущее поведение нужно проверять по коду; SQLite и переход на llama.cpp остаются планами.
