# Local Assistant

Local Assistant — настольное приложение на C++ и Qt для работы с документами и мониторинга состояния компьютера. Приложение использует локальные языковые модели для формирования ответов, RAG для поиска информации в документах и MCP для получения системных показателей.

Цель проекта — предоставить единый интерфейс для запросов к документам и данным компьютера с отображением источников ответа. Проект находится в активной разработке.

## Что уже работает

- Интерфейс чата с несколькими диалогами и переключением между ними.
- Переписка и поле ввода расположены в центральной колонке шириной до 1040 пикселей. Пустое поле ввода компактное и растёт по мере набора вопроса; длинный черновик прокручивается внутри поля. Ответы используют до 900 пикселей ширины, высота пересчитывается при изменении размера окна. Минимальный размер окна — 1100×680. Длинные строки кода и широкие таблицы прокручиваются горизонтально внутри ответа и не растягивают всю переписку; индикатор ожидания занимает одну компактную строку.
- Удаление чата правой кнопкой мыши → «Удалить чат»: сообщения, документы, индекс и неиспользуемые другими чатами постоянные копии изображений удаляются вместе. Исходные файлы пользователя сохраняются. После удаления последнего чата создаётся новый пустой.
- Постепенный вывод ответа через SSE в исходном чате: текст дополняется в одном сообщении, Markdown отображается по мере поступления. Кольцо «Готовлю ответ» сменяется на «Пишу ответ». Можно переключать чаты и возвращаться к поступающему ответу; прокрутка вверх не сбрасывается каждым обновлением.
- PostgreSQL сохраняет чаты, сообщения, документы, изображения, чанки, embeddings и снимки источников вопросов. После перезапуска восстанавливаются последний чат и его готовый индекс.
- Загрузка TXT, PDF, DOCX, DOC и отдельных изображений PNG, JPG/JPEG, WEBP, BMP, проверка дубликатов и отображение состояния индексации.
- Асинхронное чтение текста, таблиц и встроенных фотографий. PDF обрабатывается существующим комплектом Poppler (`pdftohtml`, `pdftoppm`), DOCX — `python-docx`. DOC сначала преобразуется в DOCX установленным Word либо LibreOffice.
- Автоматическое распознавание изображений и сканов локальной Qwen3-VL: описание и видимый текст попадают в поиск. Для найденных изображений модель получает сами картинки вместе с вопросом. Отдельного переключателя OCR нет.
- Через «+» к сообщению прикрепляется до четырёх документов или фотографий. Перед отправкой видны карточки файлов с возможностью убрать вложение; после отправки карточки остаются под вопросом. Фото открывается для просмотра по нажатию на миниатюру. Кнопка «Добавить файл» во вкладке «Документы» по-прежнему загружает материалы в базу текущего чата без отправки вопроса.
- Поворот фотографий по EXIF учитывается, исходный файл не изменяется. Для распознавания нужен настроенный `mmproj`; повреждённые файлы и анимированные изображения дают понятную ошибку.
- Прогресс чтения, распознавания и индексации сверху окна, отмена обработки, предупреждения о непрочитанных изображениях и кэш описаний.
- Разбиение текста на чанки, пакетное получение embeddings и поиск подходящих фрагментов для ответа.
- Генерация ответов через локальный llama-server из llama.cpp. Два сервера запускаются приложением автоматически: Qwen для ответов и EmbeddingGemma для поиска.
- Получение загрузки CPU и RAM через собственный MCP-сервер на Python.
- Отображение источников ответа и тёмная тема интерфейса.
- Постоянная строка состояний обоих серверов сверху окна и раскрываемый журнал. Готовность проверяется через /health; до загрузки моделей отправка вопросов и документов отключена.
- Отображение Markdown в ответах ассистента через преобразование в HTML библиотекой MD4C. Сообщения пользователя отображаются обычным текстом.

Чаты и обработанные документы сохраняются в PostgreSQL. Во время обработки можно открывать и создавать чаты; задача сохраняет исходный chatId, документы и индекс, поэтому её результат не попадает в другой чат. В памяти находятся рабочий набор и набор открытого чата. Новые вычисления пока запускаются по одному; навигация и ввод черновика доступны во время ожидания. Статус работы виден в списке чатов. TXT читаются в UTF-8; процессы чтения документов передают JSON в UTF-8. DOCX сохраняет порядок текста и картинок в абзацах, читает таблицы, вложенные таблицы, изображения в ячейках и колонтитулах. Для объединённых ячеек содержимое не дублируется. PDF сохраняет номера страниц; DOC/DOCX не имеют надёжной пагинации без вёрстки, поэтому для них страницы не выдумываются.

Размер исходного файла по умолчанию ограничен 100 МиБ (`documents/maxFileSizeMiB`). Извлечённый JSON ограничен 64 МиБ. Обрабатывается один документ за раз; вопросы во время обработки отключены, доступна отмена. Таймаут без сообщений прогресса — 6 минут, утилиты Poppler или конвертера DOC — 3 минуты. Для ответа чата таймаут зависит от предела генерации: 250 мс на разрешённый токен, от 5 до 30 минут; отбор контекста и распознавание изображения ограничены 5 минутами. Документы с сотнями фотографий требуют значительно больше времени, чем текстовые; ограничения на количество страниц нет.

После чтения документы проходят общую очередь индексации. Чанки имеют размер до 500 символов QString (единиц UTF-16) с перекрытием 100. Соседние текстовые абзацы объединяются; границы страниц PDF, таблиц и изображений сохраняются. Это не создаёт отдельный embedding для каждого короткого абзаца. Блоки сохраняют страницу PDF, таблицу/ячейку и путь изображения; описания изображений явно помечены как результат модели. TXT разбивается как обычный текст. Embeddings запрашиваются пакетами до 16 текстов. Проверяются количество результатов, индексы, размерность и числовые значения векторов. Новый индекс собирается отдельно и становится рабочим после успешного сохранения в БД. При ошибке или отмене повторной индексации сохраняются предыдущие текст, статус и рабочий индекс документа; неудачная первая загрузка получает статус ошибки. Документ со статусом ошибки или предупреждения можно загрузить повторно.

Если при восстановлении чата отсутствует сохранённая картинка, только соответствующий документ получает статус ошибки и исключается из поиска. Остальные документы и переписка доступны; недостающий файл указан в подсказке документа. После восстановления картинки перезапустите приложение либо повторно загрузите документ, чтобы восстановить доступ к поиску.

Ошибки отдельных изображений не теряют успешно прочитанный текст: документ получает статус «Готов с предупреждениями», подробности находятся в журнале и подсказке в списке документов. Если доступного текста нет совсем, загрузка завершается ошибкой. Описания кэшируются в папке данных приложения `cache/document-images/descriptions`; ключ учитывает картинку, модель, проектор и версию инструкции. Одинаковая картинка повторно не распознаётся после успешного результата. Кэш не заменяет сохранение чатов или индекса.

Для иллюстраций модель получает инструкцию дать краткое описание для поиска: тему, читаемые подписи и основные связи элементов. Для изображений страниц текста и таблиц инструкция требует полного чтения. Для графиков запрещено создавать таблицы предполагаемых значений по кривым; соблюдение инструкции моделью не гарантируется. Это сокращает лишнюю генерацию, но не гарантирует точность чисел, мелкого текста, рукописных записей и сложных схем. После смены версии инструкции старые описания не используются: первое чтение заново распознаёт картинки, последующие используют новый кэш.

Изображения уменьшаются до 1800 пикселей по большей стороне, для модели ограничен бюджет визуальных токенов. Внешние связанные картинки DOCX не скачиваются. Диаграммы Word/SmartArt и неподдерживаемые графические объекты могут дать предупреждение; PDF с исключительно векторной графикой и текстовым слоем не имеет полного анализа всех фигур. Таблицы PDF пока читаются как текст; DOCX сохраняет строки и столбцы.

Вопрос пользователя получает отдельный embedding; поиск возвращает до 12 ближайших чанков исходного чата. Если в вопросе указано имя файла, поиск ограничивается совпавшими готовыми документами: учитываются регистр, пробелы, знаки и небольшие изменения окончаний слов, номера версий не смешиваются. `DocumentContext` расширяет найденный заголовок или строку таблицы до полной таблицы с предшествующими пояснениями и последующими примечаниями. Номер вида «таблица 5.4.1» дополнительно ищется в подписях напрямую. Одинаковые таблицы не дублируются; обычные фрагменты получают соседние абзацы. Это использует уже сохранённые блоки, повторная индексация не нужна.

Явно указанный небольшой файл (до 14 000 символов извлечённого текста и до двух изображений) передаётся целиком. При просьбе разобрать весь явно указанный файл также проверяется возможность включить его целиком. Размер проверяется реальным токенизатором: если полный запрошенный документ или таблица не помещается вместе с резервом ответа, приложение сообщает об этом и не подменяет полный разбор несколькими случайными строками. Автоматического разбора огромного документа несколькими последовательными запросами пока нет.

Перед ответом та же локальная модель выполняет короткий текстовый отбор контекста по описаниям источников и истории. Полные таблицы передаются уже в итоговый запрос; таблица/раздел и связанные изображения выбираются одной группой. Для обычной беседы документы, фотографии и MCP исключаются; для вопросов о компьютере передаётся текущий снимок CPU/RAM, для вопросов о файлах — выбранные источники. Смешанные вопросы могут использовать оба вида данных. Произвольные или повторяющиеся ID в результате отбора вызывают ошибку; возврата к отправке всего контекста нет.

Явный запрос конкретной таблицы (например, «все поля таблицы 5.4.1») включает её строки и примечания, не расширяя контекст до всего файла. Можно указать несколько таблиц. Отдельная просьба разобрать весь документ по-прежнему проверяется на вместимость целиком.

Обязательной краткости нет: полнота и формат определяются вопросом пользователя. Для разбора посылок инструкция требует перечислять поля, размеры, смещения, значения и примечания из источника. Отсутствующие или противоречивые значения нельзя додумывать. Если сервер завершил генерацию по лимиту токенов, ответ получает явную пометку «Ответ не завершён».

Отбор контекста по-прежнему возвращает один JSON; итоговая генерация использует `stream: true`. Получатель собирает SSE-события независимо от границ сетевых пакетов и UTF-8, проверяет завершение потока. UI обновляется не чаще раза в 100 мс. Без запроса системных показателей незаконченная фраза/строка удерживается до проверки фильтром, поэтому текст обычно появляется фразами или строками. Перед первым текстом модель ещё должна отобрать и обработать контекст; streaming не ускоряет сами вычисления.

Промежуточный текст хранится в памяти исходного чата. После завершения ответ записывается одной транзакцией; при сетевой ошибке уже показанный фрагмент сохраняется со статусом `failed` и пометкой «Ответ прерван», в будущий контекст такая пара не включается. При закрытии приложения во время генерации промежуточный текст не сохраняется, а сохранённый вопрос при следующем запуске будет отмечен как прерванный. Миграция `002_interrupted_answers.sql` расширяет допустимые статусы ответа без удаления истории. Ожидание первого события ограничено 5 минутами, пауза между событиями — 2 минутами; общий лимит зависит от бюджета ответа (5–30 минут).

`ContextBuilder` проверяет размер обоих запросов через `/apply-template` и `/tokenize`; отдельно резервируется место под изображения и ответ. При нехватке места старые пары исключаются только из запроса и остаются в БД. Если сам вопрос слишком большой, приложение сообщает об этом до генерации. История работает после перезапуска. В журнале отображаются бюджет, число выбранных пар/источников и наличие MCP; в снимке источников сохраняются только данные итогового запроса. Отбор добавляет один короткий вызов модели и может ошибаться в определении темы. Переформулирование поискового вопроса по истории и автоматические резюме ещё не реализованы.

Показатели компьютера разрешаются отдельным правилом `system_status_policy`: по явному вопросу о текущей нагрузке либо короткому уточнению такого вопроса. На остальные запросы MCP не передаётся; известные вставки с показателями удаляются из копии старых ответов перед отправкой модели и проверяются в новом ответе до показа и сохранения. История в БД при этом не переписывается. Проверка сохраняет примеры кода и подтверждённые числовые сведения выбранных документов; она использует языковые шаблоны и не заменяет полноценное понимание произвольной формулировки. Постоянная строка CPU/RAM внизу приложения работает независимо от ответов.

## Вложения сообщений

Нажмите «+», выберите файлы, напишите вопрос и отправьте сообщение. Для фотографии достаточно вопроса «Как это исправить?» или «Что здесь указано?»: модель получает пиксели именно этого вложения. Без текста отправляется запрос описать содержимое файлов. Непосланные текст и файлы остаются отдельными черновиками каждого чата в памяти приложения; после закрытия черновики не восстанавливаются.

Сначала сохраняются вопрос и список вложений, затем файлы последовательно читаются и индексируются общим обработчиком. Только после успешного сохранения всех вложений начинается ответ. При ошибке или отмене вопрос помечается как неудавшийся; модель не отвечает без недоступного файла. Уже обработанные файлы остаются в списке документов чата. Повторное прикрепление перечитывает файл и обновляет индекс, сохраняя UUID документа; кэш описаний изображений продолжает использоваться.

Для текущего вопроса поиск ограничен прикреплёнными файлами. Маленькие документы и фотографии включаются целиком, большие — через найденные связанные разделы; действуют обычные ограничения контекстного окна. Явное вложение не может быть отброшено только из-за того, что модель отбора назвала короткий вопрос обычной беседой. Следующие сообщения без вложений используют общую базу чата и историю, в которой указаны имена ранее прикреплённых файлов.

Миграция `003_message_attachments.sql` добавляет связи сообщений с документами и сохранёнными изображениями. Карточки восстанавливаются из БД, копия фотографии доступна после удаления оригинала. Исходные PDF/DOCX/TXT целиком не копируются: сохраняются их извлечённое содержимое, индекс и сведения о вложении. Обновление схемы применяется автоматически при запуске, старые сообщения получают пустой список вложений.

## Стек

C++17, Qt 5 Widgets и Network, CMake. Сборка проверена с Qt 5.7 и MinGW 5.3 (32 бита). Для документов — отдельный процесс Python с `python-docx==1.2.0` и `Pillow==12.3.0`, существующий Poppler 26.09.0; PyMuPDF не требуется. Для MCP — Python, MCP SDK и psutil. Python 3.12 и 3.13 поддерживаются; окружение создаётся на целевом компьютере. MD4C 0.5.2 собирается из исходников на C. Используются EmbeddingGemma 300M QAT Q8_0 и Qwen3-VL-8B-Instruct Q4_K_M с соответствующим `mmproj` F16. llama.cpp b11429 работает отдельными 64-битными процессами, клиент Qt остаётся 32-битным.

## Структура исходников

- `include/` — заголовки `.h` и `.hpp`.
- `src/` — реализации `.cpp` и точка входа `main.cpp`; форма окна остаётся в `src/ui/`.
- В обеих папках сохраняется разделение на `application`, `chat`, `documents`, `io`, `llm`, `mcp`, `rag` и `ui`.
- Например, объявление загрузчика находится в `include/io/document_loader.hpp`, реализация — в `src/io/document_loader.cpp`.
- `document_tools/` — общий обработчик `read_document.py`, чтение DOCX/PDF и отдельных фотографий (`read_image.py`), преобразование DOC, нормализация картинок, клиент vision и кэш описаний.
- `mcp_server/` — MCP-сервер для получения CPU/RAM.
- `storage_tools/` — отдельный Python-процесс хранения, psycopg, запуск своего PostgreSQL и SQL-миграции; `include/storage` и `src/storage` — асинхронный клиент Qt и сериализация.
- `third_party/md4c/` — исходники библиотеки преобразования Markdown в HTML, необходимые для сборки.
- `architecture/` — актуальные диаграммы, схема PostgreSQL и описание реализованных решений и дальнейших улучшений.

Новые заголовки и реализации нужно добавлять в `CMakeLists.txt`. Актуальный способ сборки — CMake. `IndustrialAiAssistant.pro` сохранён как прежний проект qmake, но пока не обновлён под все новые обработчики документов и MD4C.

Чтение документов разделено интерфейсом `IDocumentReader`. `DocumentLoader` выбирает `TxtDocumentReader` или `StructuredDocumentReader` для PDF/DOC/DOCX и фотографий. Отдельная фотография становится документом с одним блоком изображения без номера страницы. Общий `DocumentExtractor` управляет `QProcess`, таймером, прогрессом и отменой; `document_content_parser.cpp` проверяет JSON и соответствие текста блокам. Форматные различия остаются в Python-модулях. `DocumentManager` добавляет результат, а `AssistantService` запускает индексацию через `EmbeddingClient`. Прежние дублирующиеся PDF/DOCX-экстракторы заменены общим.

Markdown преобразуется только при отображении ответа: `MessageWidget` вызывает `markdownToHtml()` из `src/ui/markdown_render.cpp` и показывает HTML через `QLabel`. В `ChatMessage` сохраняется исходный текст ответа. Внешний вид ограничен возможностями HTML, поддерживаемого Qt; это не браузерный движок.

## Запуск

1. Открыть `CMakeLists.txt` в Qt Creator и выбрать комплект Qt 5.7 / MinGW 5.3 (32 бита). Исходники MD4C находятся в `third_party/md4c/`.
2. Подготовить файлы относительно папки проекта или переносимой папки приложения:
   - `tools/llama-cpp/llama-server.exe` и все DLL из Windows x64 CPU-сборки llama.cpp b11429;
   - при наличии NVIDIA GPU: `tools/llama-cpp/cuda/llama-server.exe` и DLL из CUDA 12.4-сборки и соответствующего архива cudart;
   - `models/Qwen3-VL-8B-Instruct-Q4_K_M.gguf`;
   - `models/mmproj-Qwen3-VL-8B-Instruct-F16.gguf` — проектор именно этой VL-модели;
   - `models/embeddinggemma-300m-qat-Q8_0.gguf`;
   - полный комплект `tools/poppler-26.09.0/Library/bin/`, включая `pdftohtml.exe` и `pdftoppm.exe` и DLL;
   - `tools/postgresql/bin`, `lib` и `share` из [официального Windows x64 архива PostgreSQL](https://www.enterprisedb.com/download-postgresql-binaries); локально проверена версия 17.11;
   - для DOC — установленный Microsoft Word (проверено локально) либо LibreOffice с путём `documents/soffice` в INI. Путь LibreOffice предусмотрен, но локально не проверен.
3. Установить Python 3.12 или 3.13 и создать окружения **на том компьютере, где запускается приложение**. Пример для 3.13 (для 3.12 заменить версию в командах):

   ```powershell
   py -3.13 -m venv mcp_server/.venv
   ./mcp_server/.venv/Scripts/python.exe -m pip install -r mcp_server/requirements.txt
   py -3.13 -m venv document_tools/.venv
   ./document_tools/.venv/Scripts/python.exe -m pip install -r document_tools/requirements.txt
   py -3.13 -m venv storage_tools/.venv
   ./storage_tools/.venv/Scripts/python.exe -m pip install -r storage_tools/requirements.txt
   ```

Для `storage_tools` нужен 64-битный Python. На офлайн-компьютере зависимости устанавливаются из заранее скачанных wheels подходящей версии Python: `pip install --no-index --find-links <папка-wheels> -r storage_tools/requirements.txt`. `.venv` с другого компьютера не переносится.

Для текущего рабочего ПК подготовлены wheels Python 3.12 x64 в игнорируемой папке `build-storage-setup/wheels`. Для обновления понадобятся новый `.exe`, исходники `storage_tools` вместе с `migrations`, `tools/postgresql` (`bin`, `lib`, `share`) и новые параметры INI. Существующая `storage-data` принадлежит конкретной установке: не заменяйте её пустой папкой от другой сборки.

4. Остановить вручную запущенные серверы на портах 8080 и 8081. Для собственной PostgreSQL используется 55432, настраивается через `storage/port`. Приложение сообщает о занятом порте и не останавливает чужие процессы.
5. Собрать и запустить приложение. Серверы моделей запускаются после создания окна. Сверху отображаются запуск, загрузка модели, готовность или ошибка; кнопка «Журнал» раскрывает сообщения серверов и историю состояний. Журнал содержит последние 500 строк и хранится в памяти.

Настройки находятся в `local-assistant.ini`: `backend=auto`, `cpu` или `cuda`, пути GGUF, `chatMmproj`, порты, таймаут запуска, `chatGpuLayers`, `chatKvCacheType`, `mmprojGpu`, `chatContextSize`, `maxAnswerTokens`. Для текущего ноутбука RTX 4050 6 ГБ сохранено 20 слоёв Qwen на GPU, KV-кэш `f16` и контекст 16384; проектор работает на GPU. Кэш хранит промежуточные данные контекста, файл модели при этом не меняется. Допустимы `f16` и `q8_0` (для K и V вместе); Q8 включает Flash Attention. На CPU используется F16. Без нового параметра также используется F16. Эффективные настройки памяти отображаются в журнале Qwen.

В сравнительном замере на этом ноутбуке (llama.cpp b11429, 4984 входных токена, 192 выходных, EmbeddingGemma загружена) эксперимент с 24 слоями/Q8 вместо 20/F16 повысил скорость генерации примерно с 10 до 14 токенов/с; полное время запроса снизилось с 24,3 до 18,6 с. Общая занятая VRAM после текстового/графического запроса составила около 5,6 ГиБ из 6 ГиБ. Тестовая табличка прочитана правильно в обеих конфигурациях. Однако эксперимент с Q8 не прошёл проверку релевантности: на «Спасибо» модель повторила посторонние сведения из старой истории. Поэтому Q8 пока оставлен как опция, а в INI сохранён F16; один такой прогон не доказывает, что причиной был именно кэш. Скорость зависит от длины контекста, нагрузки и документа. Перенос проектора на CPU дал дополнительное ускорение текста в коротком тесте, но замедлил обработку изображения, поэтому `mmprojGpu=true` сохранён. При нехватке VRAM сначала уменьшите `chatGpuLayers`.

Ответ ограничен 6144 токенами; допустимый диапазон — от 128 до половины окна. Настройки читаются при запуске. Увеличение окна или числа слоёв требует проверки свободной видеопамяти вместе с сервером embeddings. В режиме `auto` CUDA проверяется через `--list-devices` (до 5 секунд); иначе выбирается CPU. Для диагностики можно задать `LOCAL_ASSISTANT_BACKEND=cpu` только для запуска процесса. Идентификаторы API — `local-chat` и `embeddinggemma`. Без проектора текстовый чат продолжит работать, изображения дадут явное предупреждение.

Оба сервера привязаны к 127.0.0.1. На загрузку модели по умолчанию отводится 120 секунд, `/health` проверяется каждые 500 мс, таймаут одного HTTP-запроса — 3 секунды. При обычном закрытии окно ждёт завершения обоих серверов. На Windows собственные процессы серверов включены в Job Object: при принудительной остановке приложения (например, Stop в Qt Creator) Windows также завершает эти процессы. Ошибка подключения к Job Object отображается в журнале; тогда остаётся обычная остановка через QProcess. MCP запускается автоматически, обработчики PDF/DOCX — при загрузке документа.

Папка данных определяется относительно `.exe`: ищутся `models/` и `tools/llama-cpp/` рядом с программой или в родительских папках (поддерживается запуск из `build-qtcreator`). Пути не привязаны к диску C. Добавлять Python, Poppler или llama.cpp в глобальный PATH не нужно. Само приложение и Qt DLL должны соответствовать друг другу; для рабочего компьютера нужна 64-битная Windows, поскольку llama-server — x64.

Для запуска `.exe` вне Qt Creator рядом с ним нужны Qt DLL и плагины. Для текущего комплекта:

```powershell
cmake -E env --modify PATH=path_list_prepend:C:/Qt/QT/Tools/mingw530_32/bin --modify PATH=path_list_prepend:C:/Qt/QT/5.7/mingw53_32/bin C:/Qt/QT/5.7/mingw53_32/bin/windeployqt.exe --release --compiler-runtime --no-translations ./build-qtcreator/IndustrialAiAssistant.exe
```

Для переноса можно скопировать структуру проекта с `build-qtcreator`, `models`, `tools`, `local-assistant.ini`, `document_tools` и `mcp_server`. На компьютере без GPU CUDA-папку копировать не обязательно. `.venv` создаётся заново; копировать окружение Python 3.13 поверх 3.12 нельзя. Qt Creator и компилятор на рабочем компьютере не нужны. Отсутствие Python влияет на MCP и чтение PDF/DOC/DOCX; серверы моделей запускаются независимо.

При обновлении уже работающей офлайн-установки нужны новый `IndustrialAiAssistant.exe`, все `.py` и `convert_doc.ps1` из `document_tools`, обновлённый `requirements.txt`, новые параметры INI и соответствующий `mmproj` в `models`. Уже установленные Qt DLL, Poppler и модели повторно переносить не нужно. Для нового Pillow подготовлены локальные колёса Python 3.12 x64/x86 в игнорируемой папке `build-document-transfer/wheels`. Установка на рабочем ПК из корня приложения:

```powershell
./document_tools/.venv/Scripts/python.exe -m pip install --no-index --find-links ./build-document-transfer/wheels Pillow==12.3.0
```

## Проверка документов и интерфейса

БД автоматически создаётся при первом запуске в `storage-data/` (можно изменить `storage/dataDirectory`). Там находятся кластер PostgreSQL, автоматически созданные учётные данные и постоянные изображения. Эта папка и бинарники исключены из Git. Системная служба не устанавливается, глобальный PATH не меняется. При ошибке БД приложение показывает её состояние сверху и блокирует новые операции вместо скрытого перехода к несохраняемой истории. При первом переходе с версии без БД прежние данные из RAM восстановить невозможно — их нужно загрузить заново.

Проверка сохранения: создать два чата, загрузить разные файлы, отправить вопросы, закрыть приложение обычным крестиком и запустить снова. Сообщения и файлы должны восстановиться в своих чатах без повторной индексации. Проверить список источников. При прерывании генерации вопрос после перезапуска помечается ошибкой. Ответ, который не удалось записать в БД, помечается «Не сохранено».

Проверка навигации и истории: в первом чате сообщить «Код проекта ALPHA-781», во втором — «Код проекта BRAVO-926». Затем в каждом спросить «Какой код проекта я назвал?». Пока готовится ответ, переходить в другой чат: ответ должен появиться только в исходном. Аналогично переключиться во время загрузки документа. Черновики разделены по чатам в памяти, но после закрытия приложения пока не сохраняются.

Проверка удаления: правой кнопкой нажать на ненужный чат и выбрать «Удалить чат». Он должен исчезнуть вместе с документами и не восстановиться после перезапуска. Одинаковый файл, добавленный в другой чат, должен остаться доступным. Чат с незавершённым ответом или обработкой документа удалить нельзя; другие чаты доступны для удаления. Исходные файлы и общий кэш распознавания не удаляются. Ошибка очистки постоянной копии изображения выводится как предупреждение после успешного удаления чата из БД.

Проверка ожидания: отправить вопрос, увидеть кольцо под сообщениями, перейти в другой чат и вернуться. Индикатор принадлежит исходному чату и пропадает при ответе или ошибке. Старую текстовую приписку «Ожидание ответа…» внутри сообщения пользователя заменяет этот индикатор.

PostgreSQL записывает документ, блоки и все embeddings одной транзакцией. SHA-256 модели и версия подготовки текста определяют совместимость векторов; при смене модели документ требует повторной загрузки. Постоянные изображения копируются из кэша в `storage-data/images`. Для переноса всей папки данных сначала полностью закрыть приложение и дождаться остановки его PostgreSQL. Подробная архитектура и ограничения: [architecture/README.md](architecture/README.md).

Для локальных проверок подготовлены `test-document.pdf` и `test-document.docx` — небольшие документы с русским текстом и вымышленными данными. Тестовые PDF, корневой тестовый DOCX и папка `test-documents/` исключены через `.gitignore` и не появятся автоматически после клонирования репозитория. При их отсутствии можно использовать собственный небольшой документ с заранее известными фактами.

- PDF: загрузить `test-document.pdf`, дождаться статуса «Готов» и спросить: «Сколько датчиков установлено в проекте “Северный маяк”?». Ожидаемый ответ — 12; в источниках должны отображаться фрагменты этого PDF.
- DOCX: загрузить `test-document.docx`, проверить чтение абзацев до и после таблицы и спросить количество датчиков температуры. Ожидаемый ответ — 12; в источниках должен быть этот DOCX.
- Фотография: через «+» выбрать PNG/JPG/JPEG/WEBP/BMP с читаемой надписью, дождаться статуса «Готов» и спросить о ней. Источник должен указывать на исходный файл фотографии. Проверить также файл с русским именем, фотографию с поворотом EXIF и повреждённый файл. После перезапуска повторная загрузка использует кэш распознавания.
- Большие DOCX: локальные файлы `test-documents/load-test-100-pages.docx` и `test-documents/load-test-500-pages.docx` содержат разделы с явными разрывами страниц. Проверить поиск фактов из начала, середины и конца документа. Итоговая пагинация зависит от приложения, в котором открыт DOCX.
- Markdown: попросить ответ с заголовком, жирным текстом, списком и блоком кода. Проверить форматирование, переносы и выделение текста мышью.
- Вложения: выбрать фото и TXT через «+», удалить лишнюю карточку до отправки, задать вопрос без имени файла, во время обработки сменить чат и вернуться. После перезапуска проверить карточки и просмотр фото. Повреждённое вложение и отмена должны завершать вопрос ошибкой без выдуманного ответа. Загрузка через вкладку «Документы» должна по-прежнему работать без отправки вопроса.

Дополнительно проверить фотографию в абзаце и таблице DOCX, старый DOC с той же фотографией, PDF со сканом, повёрнутый PDF, отмену и повторную загрузку, повреждённый документ и TXT. Для PDF источники показывают страницу; позиции обозначают смещения в извлечённом тексте. В DOCX картинки в таблицах показывают также номер таблицы, строки и столбца (с единицы).

Автоматические проверки:

Отдельный `message_attachments_test` проверяет фото + TXT с настоящей моделью, изоляцию от остальных документов, переключение чата, повторную загрузку, повреждённый файл, отмену индексации и постоянную копию фотографии. Он создаёт временную БД на порту 55436 и запускает серверы моделей с настройками проекта; запускайте при закрытом приложении. Сборка: `cmake --build build-qtcreator --target message_attachments_test` в окружении Qt/MinGW; запуск: `build-qtcreator/message_attachments_test.exe test-documents/images/standalone-plate.png` (нужна локальная тестовая фотография).

```powershell
./document_tools/.venv/Scripts/python.exe -m unittest discover -s tests -p test_document_tools.py -v
./storage_tools/.venv/Scripts/python.exe -m unittest discover -s tests -p test_storage.py -v
cmake -E env --modify PATH=path_list_prepend:C:/Qt/QT/Tools/mingw530_32/bin cmake -S . -B build-qtcreator -DLOCAL_ASSISTANT_BUILD_TESTS=ON
cmake -E env --modify PATH=path_list_prepend:C:/Qt/QT/Tools/mingw530_32/bin cmake --build build-qtcreator
ctest --test-dir build-qtcreator --output-on-failure
```

Тест `document_pipeline_test` проверяет схему JSON, смещения чанков и происхождение изображений. `context_builder_test` проверяет подбор истории, целостность пар, резерв изображений, ошибки и отмену на локальном HTTP-стенде. Дополнительные `service_pipeline_test` и `chat_context_integration_test` собираются отдельными целями и запускают настоящие серверы из INI; им передаётся путь к тестовому документу с табличкой `PUMP-417 / 7.5 bar`. Они не входят в обычный `ctest`. Для них нужно задать отдельные `LOCAL_ASSISTANT_STORAGE_DIR` и `LOCAL_ASSISTANT_STORAGE_PORT`. Второй тест проверяет переключение во время обработки и записи вопроса, разные истории двух чатов и бюджет реальным токенизатором.

`context_builder_test` также проверяет фильтрацию источников/MCP, старых вставок CPU/RAM и нового ответа, валидацию JSON и отмену во время отбора. Отдельная цель `context_relevance_test` проверяет сценарии через реальный LLM-клиент: имя с посторонними данными в старой истории, документы, CPU/RAM, уточнения и смешанные вопросы. Ему передаются URL уже запущенного тестового llama-server, например `http://127.0.0.1:8088/v1/`, и путь к `test-documents/images/standalone-plate.png`; необязательный третий аргумент — JSON с `question` и массивом `history` из пар `question`/`answer`. Тест не использует БД и не входит в `ctest`.

`chat_ui_integration_test` собирается отдельной целью и запускается из корня проекта. Он самостоятельно создаёт временную PostgreSQL на порту 55433, не запускает модели и проверяет меню удаления, переключение во время удаления, очистку документов, последний чат и работу анимации. PNG-превью сохраняются в `build-qtcreator/`. Для запуска без окна: `cmake -E env QT_QPA_PLATFORM=offscreen QT_PLUGIN_PATH=C:/Qt/QT/5.7/mingw53_32/plugins ./build-qtcreator/chat_ui_integration_test.exe`. `test_storage.py` дополнительно проверяет каскадное удаление, общие изображения, сохранность оригиналов и ошибки очистки файлов.

`document_context_test` входит в `ctest`: проверяет выбор файла с пробелами/номером версии, изоляцию поиска, раскрытие таблицы по заголовку и номеру, примечания, исключение дубликатов и связь с изображениями. `document_retrieval_test` — отдельная ручная цель для реальных моделей; аргументы: URL чата `/v1/`, URL embeddings `/v1/`, локальный JSON с `question`, `documents`, `entries` и необязательными `expectedSections`. Тест не изменяет БД, сохраняет фактически переданные источники и ответ рядом с фикстурой. Реальные документы и такие фикстуры не добавляются в Git.

В локальном замере обработки тестового DOCX на 500 страниц время снизилось с 35,29 до примерно 27 секунд после перехода на пакеты по 16 чанков. Это результат на текущем компьютере и модели, а не гарантированная скорость на другом оборудовании. Для сравнения использовать тот же документ и одинаковые границы замера, с уже загруженной моделью. Между повторными загрузками одного файла перезапускать приложение из-за проверки дубликатов.
