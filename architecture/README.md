# Хранение и контекст Local Assistant

## Решение

PostgreSQL хранит чаты, сообщения, извлечённое содержимое документов, чанки и embeddings. Это локальная однопользовательская версия. Qt не выполняет SQL: `StorageClient` асинхронно общается по JSON lines через stdin/stdout с `storage_tools/server.py`. Python-репозиторий использует psycopg 3 и параметризованные SQL-запросы. Такое разделение сохраняет Qt 5.7 / MinGW 32-bit и позволяет использовать современный 64-битный PostgreSQL без 32-битного libpq.

Отдельные процессы уже применяются для моделей и чтения документов; хранилище следует той же схеме. Оно не является MCP-инструментом и не предоставляет модели произвольный доступ к SQL.

## Границы компонентов

| Компонент | Ответственность |
|---|---|
| `ChatManager` | Текущий чат, порядок сообщений в UI, сохранение вопроса до генерации, связь ответа с вопросом |
| `AssistantService` | Одна активная операция, обработка документов, поиск, подготовка и сохранение источников |
| `DocumentManager` | Только документы открытого чата и их состояния |
| `StorageClient` | Асинхронный протокол процесса, таймаут, ошибки, штатное завершение |
| `storage_tools/repository.py` | SQL-миграции, короткие транзакции и проверка совместимости векторов |
| `storage_tools/runtime.py` | Собственный кластер PostgreSQL, запуск/остановка, учётные данные |
| `InMemoryVectorStore` | Точный cosine search по готовым векторам одного текущего чата |

UI не зависит от SQL-таблиц. Смена библиотеки доступа или переход на сервер приложений не требует переписывать виджеты. `repository.py` содержит явные операции, а не универсальный вызов SQL по запросу клиента.

## Владение данными

- `chats` владеет `messages` и `documents`. UUID документа отделён от исходного пути. Один файл можно независимо добавить в два разных чата.
- `messages.position` задаёт стабильный порядок; это sequence базы, пропуски после отката допустимы. Ответ содержит `reply_to`; составной внешний ключ не допускает ссылку на вопрос чужого чата. Репозиторий дополнительно проверяет роль исходного сообщения.
- `messages.context_snapshot` сохраняет текст источников и снимок MCP, отправленные с конкретным вопросом. Источники старого ответа не зависят от текущего поиска. UI пока показывает последние источники открытого чата; просмотр источников отдельно у каждого сообщения можно добавить позже.
- `documents` хранит исходный путь, хеш, извлечённый текст, предупреждения и версию обработки. `document_blocks` сохраняет структуру текста, таблиц и изображений; форматные поля находятся в JSONB.
- `chunks` хранит текст, смещение UTF-16, сведения об источнике и массив `double precision[]`. Размерность, конечность и ненулевая норма проверяются при записи. Никакой памяти `std::vector` напрямую в SQL не сохраняется.
- `embedding_profiles` идентифицирует SHA-256 файла модели, размерность и версию подготовки входа. Векторы разных моделей не смешиваются даже при одинаковой длине. При несовпадении профиля или версии обработки документ требует повторной загрузки.
- Изображения копируются из временного кэша в постоянную `storage-data/images` под SHA-256-именами. В БД находятся относительные имена, поэтому папка данных может переехать. Оригиналы PDF/DOCX отдельно не копируются: для восстановления доступны извлечённый текст, блоки и изображения.
- `app_settings` хранит последний открытый чат. `schema_migrations` содержит номера и контрольные суммы применённых SQL-файлов.

## Транзакции и сбои

Вопрос сначала сохраняется как `pending`, затем передаётся сервису. Источники сохраняются до отправки запроса LLM. Ответ и завершение вопроса записываются одной транзакцией. При ошибке записи полученный ответ остаётся в UI с пометкой «Не сохранено»; сейчас нет отдельной кнопки повторного сохранения. После перезапуска незавершённые вопросы получают `failed`, автоматической повторной генерации нет.

Чтение и вычисление embeddings выполняются вне SQL-транзакций. Готовый документ, его блоки и все векторы записываются одной короткой транзакцией. При ошибке сохранения документ исключается из текущего поискового индекса. Прерванная новая загрузка не появляется в БД как готовая; пользователь может повторить её. При неудачной замене уже сохранённая версия остаётся целой в БД.

Во время обработки, записи вопроса или ответа переключение чата запрещено. Это сознательное ограничение первой версии: оно исключает подмену индекса во время запроса. Смена чата заменяет документы и индекс только после успешного чтения и проверки нового набора.

БД запускается на `127.0.0.1:55432`. Папка `storage-data` содержит закрытый для других экземпляров приложения файл-блокировку, отдельный кластер, пароли и изображения. Системные PostgreSQL-службы не меняются. У приложения отдельная роль без прав суперпользователя; служебная роль используется только для подготовки собственной БД. При закрытии stdin worker завершает принятые записи и вызывает `pg_ctl stop -m fast`. После принудительного завершения worker следующий запуск может присоединиться к своему оставшемуся кластеру; PostgreSQL выполняет штатное восстановление WAL при необходимости.

## Контекстное окно: следующий блок

Сохранение истории и включение её в запрос модели — разные задачи. На этапе БД история уже переживает перезапуск, но текущий LLM-клиент ещё отправляет один вопрос с найденными источниками.

Следующий компонент — `ContextBuilder`: инструкции → выбранные завершённые пары сообщений текущего чата → свежие источники и изображения → текущий вопрос. Он должен резервировать место под ответ, учитывать визуальные токены и проверять размер токенизатором текущей модели. Старые пары убираются целиком; слишком большой текущий вопрос получает понятную ошибку. При смене чата история другого чата никогда не включается. У каждого чата свои данные, отдельный процесс модели для каждого чата не нужен.

Начнём с последних полных пар сообщений. Автоматические резюме длинных диалогов, query rewriting для уточняющих вопросов и pgvector оставляем отдельными улучшениями, после проверки базового поведения.

## Проверки и сопровождение

`tests/test_storage.py` поднимает отдельный временный кластер: изоляция чатов, откат неудачной замены индекса, восстановление изображений, идемпотентное сохранение ответа, смена embedding-профиля и перезапуск. C++-интеграционная проверка использует реальные модели и тот же слой хранения, что приложение.

Для резервной копии нужны PostgreSQL (`pg_dump`) и папка постоянных изображений. Для простого переноса всей `storage-data` приложение и её PostgreSQL должны быть полностью остановлены. Сырые файлы работающего кластера копировать нельзя. Миграции добавляются новыми SQL-файлами: уже применённый файл менять нельзя.

Источники технических решений: [PostgreSQL 17](https://www.postgresql.org/docs/17/), [psycopg 3](https://www.psycopg.org/psycopg3/docs/), [архивы PostgreSQL для Windows](https://www.postgresql.org/download/windows/).
