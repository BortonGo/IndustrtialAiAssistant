# Хранение и контекст Local Assistant

## Решение

PostgreSQL хранит чаты, сообщения, извлечённое содержимое документов, чанки и embeddings. Это локальная однопользовательская версия. Qt не выполняет SQL: `StorageClient` асинхронно общается по JSON lines через stdin/stdout с `storage_tools/server.py`. Python-репозиторий использует psycopg 3 и параметризованные SQL-запросы. Такое разделение сохраняет Qt 5.7 / MinGW 32-bit и позволяет использовать современный 64-битный PostgreSQL без 32-битного libpq.

Отдельные процессы уже применяются для моделей и чтения документов; хранилище следует той же схеме. Оно не является MCP-инструментом и не предоставляет модели произвольный доступ к SQL.

## Границы компонентов

| Компонент | Ответственность |
|---|---|
| `ChatManager` | Текущий чат, порядок сообщений в UI, сохранение вопроса до генерации, связь ответа с вопросом |
| `AssistantService` | Запрос чата и вложения, поиск, подготовка и сохранение источников |
| `DocumentImportQueue` | Фоновая очередь с собственным reader/index, публикация текста до vision, приоритет вопроса и сохранение прогресса |
| `DocumentManager` | Отдельные списки документов открытого чата и выполняемой задачи |
| `StorageClient` | Асинхронный протокол процесса, таймаут, ошибки, штатное завершение |
| `storage_tools/repository.py` | SQL-миграции, короткие транзакции и проверка совместимости векторов |
| `storage_tools/runtime.py` | Собственный кластер PostgreSQL, запуск/остановка, учётные данные |
| `InMemoryVectorStore` | Cosine search + BM25/RRF, приоритет обозначений, ограничения по документам; отдельный индекс для открытого чата |
| `ContextBuilder` | Шаблон модели, подсчёт токенов, выбор последних полных пар истории и источников в пределах бюджета |
| `DocumentContext` | Поиск указанного файла, раскрытие таблиц и примечаний, группировка источников и описания для отбора |

UI не зависит от SQL-таблиц. Смена библиотеки доступа или переход на сервер приложений не требует переписывать виджеты. `repository.py` содержит явные операции, а не универсальный вызов SQL по запросу клиента.

Фоновый импорт хранится в `document_imports`, промежуточные пакеты embeddings — в `document_import_chunks`. Сначала Python с `--native-only` извлекает текст/таблицы и кэширует исходные блоки вместе с путями картинок. После индексации эта версия публикуется со статусом `TextReady` (`documents.pending_images > 0`), а задание остаётся `running`. `native_done` фиксирует переход к vision, поэтому после перезапуска повторная публикация текста не нужна. Фото/сканы без текста переходят к vision без пустого документа в базе. Полный результат атомарно заменяет предварительный; старый индекс сохраняется при ошибке и отмене. При переиндексации уже опубликованного файла предварительная версия не заменяет прежнюю. Совместимые embeddings переиспользуются по точному тексту чанка; позиции и ссылки формируются заново. Маркер неполного охвата добавляется в источники для модели, только когда документ выбран для ответа. Вложения сообщения по-прежнему обрабатываются целиком перед ответом.

`SidebarWidget` отправляет ID чата из контекстного меню в `ChatManager::deleteChat`. Менеджер защищает выполняемую задачу, ждёт успешного ответа БД, затем удаляет строку модели, черновик и набор данных чата из `AssistantService`. Если пользователь успел выбрать другой чат, удаление не меняет его выбор. `ThinkingIndicator` рисует кольцо через `QPainter`; таймер работает только при видимом индикаторе. Ожидание привязано к `pendingChatId_` и заканчивается после завершения записи результата, включая ошибку.

## Владение данными

- `chats` владеет `messages` и `documents`. UUID документа отделён от исходного пути. Один файл можно независимо добавить в два разных чата.
- `message_attachments` (миграция 003) хранит порядок, имя/путь файла, связь с обработанным документом и сохранённую копию фото у конкретного сообщения. `bind_attachment` проверяет принадлежность исходному чату и соответствие пути. При переиндексации того же UUID связь сохраняется; старые фото сообщений учитываются при очистке файлов.
- `messages.position` задаёт стабильный порядок; это sequence базы, пропуски после отката допустимы. Ответ содержит `reply_to`; составной внешний ключ не допускает ссылку на вопрос чужого чата. Репозиторий дополнительно проверяет роль исходного сообщения.
- `messages.context_snapshot` сохраняет текст источников и снимок MCP, отправленные с конкретным вопросом. `source_references` (JSONB, миграция 006) хранит выбранные фрагменты с UUID/путём документа, диапазоном страниц и блоков, номерами таблиц и изображением. `DocumentContext` формирует положение по исходным блокам, `ContextBuilder` сохраняет только итоговый набор после отбора и проверки бюджета. Источники не восстанавливаются из текста, написанного моделью. Под каждым ответом кнопка «Источники» открывает материалы его вопроса через `reply_to`; старые текстовые снимки также доступны. `SourcePanel` показывает сохранённый фрагмент в отдельном окне, поэтому переиндексация или отсутствие оригинала не меняет прежний ответ. Номера страниц DOCX не выдумываются, номера таблиц обозначают порядок в файле. Открытие оригинала выполняется отдельно, только для доступного локального файла поддерживаемого формата. Встроенные ссылки и ресурсы Markdown при просмотре снимка не загружаются.
- `save_context` проверяет принадлежность документов чату вопроса и положение фрагментов. Изображение из кэша сопоставляется по хешу с уже сохранённым изображением этого документа; в JSONB записывается относительное имя копии, при чтении — полный путь текущего хранилища. Удаление чата учитывает изображения старых ответов, включая изображения прежних версий документа.
- `documents` хранит исходный путь, хеш, извлечённый текст, предупреждения и версию обработки. `document_blocks` сохраняет структуру текста, таблиц и изображений; форматные поля находятся в JSONB.
- `chunks` хранит текст, смещение UTF-16, сведения об источнике и массив `double precision[]`. Размерность, конечность и ненулевая норма проверяются при записи. Никакой памяти `std::vector` напрямую в SQL не сохраняется.
- `embedding_profiles` идентифицирует SHA-256 файла модели, размерность и версию подготовки входа. Векторы разных моделей не смешиваются даже при одинаковой длине. При несовпадении профиля или версии обработки документ требует повторной загрузки.
- Изображения копируются из временного кэша в постоянную `storage-data/images` под SHA-256-именами. В БД находятся относительные имена, поэтому папка данных может переехать. Оригиналы PDF/DOCX отдельно не копируются: для восстановления доступны извлечённый текст, блоки и изображения.
- `app_settings` хранит последний открытый чат. `schema_migrations` содержит номера и контрольные суммы применённых SQL-файлов.

## Транзакции и сбои

Вопрос сначала сохраняется как `pending`, затем передаётся сервису. Источники сохраняются до отправки запроса LLM. Ответ и завершение вопроса записываются одной транзакцией. При ошибке записи полученный ответ остаётся в UI с пометкой «Не сохранено»; сейчас нет отдельной кнопки повторного сохранения. После перезапуска незавершённые вопросы получают `failed`, автоматической повторной генерации нет.

Чтение и вычисление embeddings выполняются вне SQL-транзакций. Готовый документ, его блоки и все векторы записываются одной короткой транзакцией. При ошибке сохранения документ исключается из текущего поискового индекса. Прерванная новая загрузка не появляется в БД как готовая; пользователь может повторить её. При неудачной замене уже сохранённая версия остаётся целой в БД.

`delete_chat` блокирует строку чата и отклоняет удаление при наличии `pending`-сообщения. Чат, сообщения, документы, блоки и чанки удаляются каскадно одной транзакцией; в ней же выбирается оставшийся чат либо создаётся пустой, если удалён последний. После COMMIT worker удаляет только SHA-256-файлы из своей папки `images`, на которые больше нет ссылок в блоках или чанках. Исходные документы и общий кэш извлечения не затрагиваются. Файловая система не участвует в транзакции PostgreSQL: ошибка очистки даёт предупреждение, не отменяет уже выполненное удаление в БД; возможный остаточный файл можно убрать при будущей очистке кэша/осиротевших файлов. Запросы worker выполняются последовательно, поэтому новая запись изображения не вклинивается между проверкой ссылок и удалением.

Во время обработки можно открывать и создавать чаты. `visibleChatId_` выбирает данные на экране; `activeChatId_` закрепляет рабочие документы и индекс за выполняемой задачей. `ChatManager` сохраняет исходные `pendingChatId_` и `pendingMessageId_` до записи результата. Фоновый ответ и источники обновляют только свой чат. При загрузке выбранного чата список документов очищается, а новые вычисления блокируются до получения данных. Номер выбора защищает интерфейс от запоздавших ответов при быстрых переходах A → B → A.

Одновременно выполняется одна вычислительная задача. Пока она работает, доступны навигация, чтение истории, создание чата и ввод черновика; отправка нового вопроса и загрузка файла отключены. Статус виден в списке чатов. Черновики разделены по чатам в памяти, после закрытия приложения они не сохраняются. В RAM могут находиться рабочий и отображаемый индексы; это ограниченное число наборов, а не индекс всех чатов.

Итоговый запрос модели использует SSE. `CompletionStream` собирает события и UTF-8 из сетевых фрагментов; `LMStudioLLMClient` отправляет проверенный промежуточный текст не чаще раза в 100 мс. `AssistantService` добавляет ID исходного вопроса, `ChatManager` хранит один промежуточный ответ, а `ChatWidget` обновляет существующий `MessageWidget` только в его чате. Завершённые фразы/строки проходят фильтр непрошеной телеметрии до показа. БД не записывается на каждый токен: `finish_question` атомарно сохраняет результат. При обрыве уже показанный фрагмент получает статус `failed` и видимую пометку; миграция 002 разрешает такой статус у ответа. `question_history` выбирает только полные пары со статусами `complete`.

БД запускается на `127.0.0.1:55432`. Папка `storage-data` содержит закрытый для других экземпляров приложения файл-блокировку, отдельный кластер, пароли и изображения. Системные PostgreSQL-службы не меняются. У приложения отдельная роль без прав суперпользователя; служебная роль используется только для подготовки собственной БД. При закрытии stdin worker завершает принятые записи и вызывает `pg_ctl stop -m fast`. После принудительного завершения worker следующий запуск может присоединиться к своему оставшемуся кластеру; PostgreSQL выполняет штатное восстановление WAL при необходимости.

## Контекстное окно

`question_history` читает из PostgreSQL завершённые пары вопрос/ответ только исходного чата и только до текущего вопроса. Неуспешные, ожидающие и более поздние сообщения исключаются. Поэтому история работает и после перезапуска, независимо от того, какой чат открыт во время подготовки запроса.

Перед отбором `system_status_policy` определяет разрешение текущих измерений по словам пользователя и короткому уточнению последнего вопроса о мониторинге. Старый ответ ассистента сам по себе не даёт такого разрешения. При запрете очищается MCP и копия известных вставок CPU/RAM в истории; после генерации аналогично проверяется ответ до сигнала `answerReady`. Сохранённая история не меняется. При явном запросе мониторинга свежий снимок сохраняется независимо от ошибочного решения модели-отборщика. Документные числовые значения и fenced code сохраняются; правила ограничены поддержанными языковыми шаблонами.

`LMStudioLLMClient` сначала запрашивает у той же модели отбор данных. `context_selection.cpp` описывает четыре категории: обычная беседа, документы, текущие показатели компьютера и смешанный запрос. Модель возвращает JSON с категорией, ID источников, ID пар истории и признаком необходимости MCP. Код проверяет типы, диапазоны ID с учётом фактически показанного окна, отсутствие дубликатов, восстанавливает хронологический порядок и применяет ограничения категории. Для обычной беседы не передаются файлы и MCP, для вопроса о компьютере не передаются файлы. Факты не генерируются на этапе отбора: берутся исходные тексты выбранных элементов.

Перед поиском `DocumentContext::namedDocuments` сопоставляет имя файла в вопросе с готовыми документами исходного чата. `InMemoryVectorStore::searchHybrid` ограничивает кандидатов этими documentId до ранжирования. Внутри этого набора независимо вычисляются cosine similarity и BM25 (`k1=1.2`, `b=0.75`); первые 64 результата каждого списка (или больше, если topK выше) объединяются через RRF с константой 60. Буквальные коды, аббревиатуры в верхнем регистре, имена с подчёркиваниями и фразы в кавычках получают дополнительный приоритет. Представители разных обозначений идут первыми, чтобы сокращение контекста не потеряло второй объект сравнения. Латинские и кириллические буквы не смешиваются. При отсутствии словарных совпадений сохраняется чисто смысловая выдача. Итоговый `score` — значение ранжирования, а не вероятность правильного ответа; порядок также учитывает покрытие обозначений. Принцип объединения описан в [документации RRF](https://www.elastic.co/docs/reference/elasticsearch/rest-apis/reciprocal-rank-fusion), параметры BM25 — в [документации Lucene](https://lucene.apache.org/core/7_6_0/core/org/apache/lucene/search/similarities/BM25Similarity.html).

Словарь нормализованных слов кэшируется вместе с каждым элементом индекса в RAM. Он загружается из существующих текстов чанков без новых embeddings и без миграции БД. Добавление, замена, удаление и копирование индекса переносят обе части вместе; перед заменой проверяются векторы и готовится новый набор. Это не отдельный сервер или вторая база. Морфологический разбор и исправление опечаток в кодах не выполняются: перефразировки покрывает модель embeddings, а похожее обозначение не объявляется точным совпадением.

Затем `DocumentContext::collect` раскрывает блоки таблиц: заголовок, все строки, примечания до следующего раздела. Номер таблицы дополнительно ищется по подписям; совпадающие группы исключаются. Небольшой явно названный файл передаётся целиком; просьба обо всём названном файле также создаёт полный обязательный источник с последующей проверкой бюджета. Большие документы без такого запроса дают связанные фрагменты с явной пометкой ограниченного охвата.

Отбор получает описания расширенных источников (`selectionText`) и историю, но не пиксели изображений и не численные показатели MCP. Ответ получает исходное полное содержимое `ContextSource::text`. `groupId` связывает раздел с изображениями; `required` защищает явно запрошенный полный источник от отбрасывания в документном запросе. Для обычной беседы даже обязательные документные группы не передаются. `ContextBuilder` с `Purpose::Selection` считает размер запроса реальным токенизатором, без резерва изображений, с резервом 512 токенов под JSON. Используются ограничение JSON Schema и temperature 0. При ошибке или неполном JSON генерация ответа не запускается; запасного режима «передать всё» нет. Отбор добавляет один короткий вызов модели и может ошибиться в релевантности; полноценные резюме и переформулирование поискового запроса пока не реализованы.

Затем `ContextBuilder` собирает ответный запрос: инструкции → отобранные завершённые пары → выбранные источники/изображения/MCP → текущий вопрос. `/apply-template` возвращает шаблон текущей модели, `/tokenize` считает его текстовые токены. На каждое уникальное изображение дополнительно резервируется 1056 токенов: лимит сервера `--image-max-tokens 1024` и запас на обрамление. Это консервативный резерв, а не измеренный расход vision-энкодера. Общий запас — ещё 128 токенов. В текущем INI `models/maxAnswerTokens=6144` (допустимо от 128 до половины окна), `models/chatContextSize=16384`. При отсутствии настроек сервис использует 4096/8192 соответственно. Параметры читаются при запуске. Таймаут генерации масштабируется с пределом ответа (250 мс на токен, 5–30 минут); `finish_reason=length` даёт явную пометку незавершённого ответа.

Генерация настроена под текущую Qwen3-VL Instruct. Из [рекомендаций модели](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct#generation-hyperparameters) взяты `presence_penalty=2.0`, `top_p=1.0`, `top_k=40` для текста; с изображениями — `1.5`, `0.8`, `20` соответственно. Температура текста оставлена `0.2` вместо рекомендованной `1.0`: более творческий режим в проверке повторял посторонние сведения из старых ответов. Для изображений `temperature=0.7`. В обоих случаях `repeat_penalty=1.0`, `min_p=0.0`. Эти параметры находятся в `LMStudioLLMClient::generatePrepared`; при смене семейства модели их нужно пересмотреть. Отбор контекста в JSON по-прежнему использует temperature 0. При прежних настройках без штрафа присутствия в длинном техническом ответе наблюдалось повторение одних и тех же разделов.

Сначала проверяется запрос без истории. Если он не помещается, необязательные источники исключаются целыми группами вместе с изображениями. Таблицы не режутся по строкам; если не помещается обязательный источник, возвращается ошибка с бюджетом, без генерации по случайному остатку. Затем двоичный поиск выбирает максимальное число последних полных пар, которые входят в оставшееся место. История в БД не удаляется. Старые изображения и снимки MCP повторно не передаются; используются тексты прошлых вопросов и ответов. В журнал записываются текстовые токены, резерв изображений, резерв ответа и число включённых пар/источников. Многошагового разбора огромного документа по всем разделам пока нет.

Именно выбранный снимок источников сохраняется до генерации. При недоступности шаблона или токенизатора запрос не отправляется без проверки. Сброс и отмена инвалидируют незавершённые HTTP-ответы. Один сервер модели обслуживает все чаты последовательно; отдельные модели для чатов не создаются.

Автоматические резюме длинных диалогов, query rewriting для уточняющих вопросов и pgvector остаются отдельными улучшениями. Сейчас embedding для поиска строится по текущему вопросу: фраза «а у второго?» может потребовать более явного названия объекта, даже если история доступна генерации.

Системная инструкция различает сведения пользователя и личность ассистента, требует отвечать по теме и не повторять посторонние дополнения из старых ответов. Обязательной краткости нет: разбор каждого сообщения требует полного перечисления полей и пояснений из источника. Если таблица только упомянута, но её строк нет в контексте, ответ должен сообщать об отсутствии данных. Неподходящие кандидаты исключаются до загрузки изображений и генерации.

## Проверки и сопровождение

`tests/test_storage.py` поднимает отдельный временный кластер: изоляция чатов, откат неудачной замены индекса, восстановление изображений, идемпотентное сохранение ответа, смена embedding-профиля и перезапуск. C++-интеграционная проверка использует реальные модели и тот же слой хранения, что приложение.

`context_builder_test` проверяет бюджет, роли и целостность пар, резерв изображений, слишком большой вопрос, ошибки, отмену, валидацию отбора и отсутствие исключённых данных в реальном HTTP-запросе клиента на локальный стенд. `context_relevance_test` запускается вручную с URL работающего тестового llama-server и PNG таблички PUMP-417: имя, личность ассистента, приветствие, ненужные дополнения из старой истории, документы, CPU/RAM, смешанные и уточняющие вопросы. Он не использует БД. `chat_context_integration_test` использует реальные модели и отдельную БД: переход при обработке фотографии, быстрые переходы при записи вопроса, независимую историю двух чатов и сокращение истории реальным токенизатором.

Для резервной копии нужны PostgreSQL (`pg_dump`) и папка постоянных изображений. Для простого переноса всей `storage-data` приложение и её PostgreSQL должны быть полностью остановлены. Сырые файлы работающего кластера копировать нельзя. Миграции добавляются новыми SQL-файлами: уже применённый файл менять нельзя.

Источники технических решений: [PostgreSQL 17](https://www.postgresql.org/docs/17/), [psycopg 3](https://www.psycopg.org/psycopg3/docs/), [архивы PostgreSQL для Windows](https://www.postgresql.org/download/windows/), [API llama.cpp b11429](https://github.com/ggml-org/llama.cpp/blob/b11429/tools/server/README.md).
